A-Q1. Why should execvp() normally be called in the child rather than the shell process?
Answer: execvp() should normally be invoked by the child process since exec replaces the current process with a new one. If the shell itself calls execvp(), it will be replaced by the requested process and will no longer be able to accept new commands. Hence, shell uses fork() to create a child process, the child calls execvp() to execute the requested process, and then the parent shell waits for the child to finish using waitpid() and then displays the prompt on the shell again. 


A-Q2. Why must cd be implemented by the shell process itself rather than by a forked child?
Answer: cd must be implemented by the shell process itself, since the command changes the calling process's current working directory. If it is executed in a forked child, only the child’s working directory changes, leaving the parent shell’s working directory unchanged.


A-Q3. What problem can arise if the parent never waits for terminated child processes?
Answer: If the parent never waits for the terminated child process, the child may become a zombie process. A zombie process is such that it has finished execution but its entry still remains in the process table since the parent hasn’t collected its exit status using wait() or waitpid(). Furthermore, if too many zombie processes are accumulated, it can lead to an exhaustion of process table entries. 


B-Q1. Decompose total_jobs++ into conceptual load/modify/store steps. Why is it not an indivisible operation?
Answer: total_jobs++ consists of three steps: 
1) Load: it reads the current valud of total_jobs from memory into a register.
2) Modify: it increments the value by 1
3) Store: it writes the updated value back into memory. 

An indivisible operation is such that it occurs completely in one single step, without being 
Interrupted by another thread. Total_jobs++ is not an indivisible operation, since the three steps may not be executed as a single step. 
If two threads execute total_jobs++ concurrently, they may both read the same initial value and increment it independently, and when both threads write back their results, one increment may be lost, leading to a race condition.


B-Q2. Give an interleaving of two threads that loses one increment.
Answer: Initially, total_jobs = 0. Consider two threads, T1 and T2, executing total_jobs++ concurrently.
The following interleaving causes a lost update:
1) T1 reads total_jobs = 0.
2)T2 reads total_jobs = 0.
3) T1 increments the value and writes 1 to total_jobs.
4) T2 increments its previously read value and also writes 1 to total_jobs.
Thus, the final value of total_jobs is 1 instead of 2. One increment is lost because both threads read the same initial value, and the second thread overwrites the first thread's update. This occurs because total_jobs++ is not an atomic operation.


B-Q3. Why can the unsafe program sometimes appear to produce the expected result?
Answer: The unsafe program may sometimes produce the expected result because the threads might execute their operations one after another without interfering with each other. In such cases, each increment is completed before the next begins, so no update is lost. However, the result depends on the timing and scheduling of the threads, so the program is unreliable and may produce incorrect results during other executions.
