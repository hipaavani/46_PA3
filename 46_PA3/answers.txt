A-Q1. Why should execvp() normally be called in the child rather than the shell process?
Answer: execvp() should normally be invoked by the child process since exec replaces the current process with a new one. If the shell itself calls execvp(), it will be replaced by the requested process and will no longer be able to accept new commands. Hence, shell uses fork() to create a child process, the child calls execvp() to execute the requested process, and then the parent shell waits for the child to finish using waitpid() and then displays the prompt on the shell again. 


A-Q2. Why must cd be implemented by the shell process itself rather than by a forked child?
Answer: cd must be implemented by the shell process itself, since the command changes the calling process's current working directory. If it is executed in a forked child, only the child’s working directory changes, leaving the parent shell’s working directory unchanged.


A-Q3. What problem can arise if the parent never waits for terminated child processes?
Answer: If the parent never waits for the terminated child process, the child may become a zombie process. A zombie process is such that it has finished execution but its entry still remains in the process table since the parent hasn’t collected its exit status using wait() or waitpid(). Furthermore, if too many zombie processes are accumulated, it can lead to an exhaustion of process table entries. 


B-Q1. Decompose total_jobs++ into conceptual load/modify/store steps. Why is it not an indivisible operation?
Answer: total_jobs++ consists of three steps: 
1) Load: it reads the current valud of total_jobs from memory into a register.
2) Modify: it increments the value by 1
3) Store: it writes the updated value back into memory. 

An indivisible operation is such that it occurs completely in one single step, without being 
Interrupted by another thread. Total_jobs++ is not an indivisible operation, since the three steps may not be executed as a single step. If two threads execute total_jobs++ concurrently, they can both read the same initial value and increment it independently. Hence when both threads write back their results, one increment may be lost, leading to a race condition.


B-Q2. Give an interleaving of two threads that loses one increment.
Answer: Initially, total_jobs = 0. Consider two threads, T1 and T2, executing total_jobs++ concurrently.
The following interleaving causes a lost update:
1) T1 reads total_jobs = 0.
2)T2 reads total_jobs = 0.
3) T1 increments the value and writes 1 to total_jobs.
4) T2 increments its previously read value and also writes 1 to total_jobs.
Thus, the final value of total_jobs is 1 instead of 2. One increment is lost because both threads read the same initial value, and the second thread overwrites the first thread's update. This occurs because total_jobs++ is not an atomic operation.


B-Q3. Why can the unsafe program sometimes appear to produce the expected result?
An unsafe program can sometimes appear to even then produce the expected result because the threads might execute their operations one after another, with no interference from each other. As each increment is completed before the next occurs in this case, no update is lost. However the result can also depend on the timing and scheduling of the threads, and thus the program cannot be deemed reliable as it can produce incorrect results during other executions.


C-Q1. Why must queue head, tail, and count be protected by the same mutex?
The same mutex protects queue’s head, tail and count as multiple threads access these shared variables. Modification of the shared data by two or more threads concurrently can cause incorrect queue operations(overwriting or incorrectly tracking the number of jobs in the queue). Using the same mutex ensures correctness of the queue as only one thread will be able to modify these variables at a time.

C-Q2. Why must releasing the mutex and sleeping in pthread_cond_wait() behave atomically?
Answer: Releasing the mutex and sleeping in pthread_cond_wait() must behave atomically to prevent a thread from missing a signal from another thread. If the mutex is released before the thread starts waiting, another thread may change the queue state and signal the condition variable before the first thread begins waiting. This can cause the first thread to wait even when the condition it needs has already become true. 

C-Q3. Why must the condition around pthread_cond_wait() be checked with while rather than if?
Answer: The condition around pthread_cond_wait() must be checked using while rather than if because a thread may wake up even when the required condition is still not satisfied. For example, a consumer may wake up when the queue is still empty. Using while ensures that the condition is checked again after waking up and the thread waits again if necessary.

C-Q4. Why is pthread_cond_broadcast() appropriate during queue shutdown?
Answer: pthread_cond_broadcast() is appropriate during queue shutdown because multiple threads may be waiting on the condition variables. When the queue is shut down, all waiting threads must be woken up so they can check the shutdown condition and exit or stop submitting jobs as required. Broadcasting ensures that all waiting threads are notified instead of only one thread. 


C-Q5. Why is a condition variable preferable to busy waiting when the queue is empty for a long time?
Answer: A condition variable is preferable to busy waiting because a thread can sleep while waiting for the queue to become non-empty instead of continuously checking the queue. This prevents wasting CPU time when no jobs are available and when a job is added, the condition variable wakes up a waiting thread so it can continue execution.

C-Q6. Why can per-worker jobs_completed counters reduce synchronisation overhead compared with one shared global counter?
Answer: Per-worker jobs_completed counters reduce synchronisation overhead as each printer thread updates its own counter, avoiding the need for a mutex to protect a shared counter for every increment which would occur if multiple threads were modifying the same shared counter. The main thread adds the individual counters of all printer threads once they have finished to calculate the total number of completed jobs.


BONUS-Q. If you attempt the bonus, explain why queue_shutdown() must occur only after ALL producer threads have terminated.
Answer: queue_shutdown() must occur only after all producer threads have terminated because producers must be allowed to submit all their jobs before the queue is shut down. If the queue is shut down while producers are still running, queue_push() will fail for further submissions, and some jobs may not be submitted. Therefore, the main thread must join all producer threads before calling queue_shutdown(), ensuring that all producers have finished submitting their jobs before the printer threads are shut down.
